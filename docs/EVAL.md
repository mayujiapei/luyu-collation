# 评测与标注规范（EVAL）

> 版本：v1.0（2026-10-09）。本文件是**评测口径的唯一事实来源**：定义数据集怎么建、每条标注写什么、
> 模型输出怎么判对错、指标怎么算。**对比实验开跑前必须定稿**（HANDOFF §6）。
> 配套物：评测集与原始结果放 `docs/eval/`；Prompt 回归（另一回事）见 `server/prompts/regression/README.md`。
>
> 与其他文档的分工：`PRD §6` 定目标值，本文件定**怎么量**；`TECH_DESIGN §7` 定实验设计，本文件定**判定规则**。

## 1. 为什么需要这份规范

大模型校勘的"准确率"极易被算法地做高——放宽判对的标准、把没报的算作不适用、忽略额外报出的合法校勘点。
一旦口径含糊，后面的对比实验、论文数字、答辩结论全都不可信。所以先把口径钉死，再跑实验。

三条贯穿全篇的原则：

1. **检出与分类分开算**。模型"发现了这处有问题"和"类型判对了"是两件事，混在一个指标里会掩盖真相。
2. **额外报出的合法校勘点单列一档**，既不奖励也不惩罚——它既不是检出（不在 ground truth 里），
   也不该算误报（它可能真的对）。硬塞进任一侧都会系统性扭曲 precision 或 recall。
3. **异文类必须能给出别本依据**，否则按存疑处理。理由是实测发现模型在异文上偏积极
   （出现过 `地接衡庐 → 地连衡庐` 这类非通行异文），而"编一个合理异文"比"编一个错字"隐蔽得多。

## 2. 数据集构建

### 2.1 语料

- **来源**：公共版权古籍通行本（先秦两汉诸子、史书、笔记、骈文等），选段 200–500 字。
  来源清单进附录并注明版本出处（合规要求，见 TECH_DESIGN §9）。
- **规模**：先做 10 段作为 v1 基准（对应 PRD §6 的目标值），后续扩到数百段供论文用。
- **刻意避开**：《论语》学而篇——那是 Prompt 的 few-shot 示例，放进来会污染评测。

### 2.2 错误注入

每段必须同时具备两类错误：

| 来源 | 说明 |
|---|---|
| 天然 OCR 错误 | 由 OCR 工具识别真实书影产生，反映真实分布 |
| 人工注入错误 | 我方按类型定向构造，保证五类都有足够样本 |

- **总量**：全数据集 ≥60 个错误点（PRD §6）。
- **五类配额**：讹字 / 衍文 / 脱文 / 通假 / 异文 各 ≥10 个，避免某类样本太少导致该类指标没有意义。
- **注入手段**（与校勘类型对应的典型形态）：
  - 讹字：形近字替换（`伐`→`代`、`未`→`末`）
  - 衍文：误重一字（`太丘舍去`→`太丘舍舍去`）
  - 脱文：脱去虚实字（`其名为鲲`→`其名鲲`）
  - 通假：**不注入**——通假不是错误，而是需要标注的用字现象，样本取自原文本身（如「蚤」通「早」）
  - 异文：替换为**有版本依据的**他本写法（如「豫章故郡」/「南昌故郡」），并在标注里注明依据

### 2.3 标注记录格式

每个错误点一条记录，`docs/eval/` 下存为 JSON（与代码同级，便于脚本直接读）：

```json
{
  "id": "case-003-point-2",
  "caseId": "case-003",
  "start": 6,
  "end": 7,
  "original": "代",
  "expectedSuggestion": "伐",
  "type": "讹字",
  "path": ["形近", "版本"],
  "hasEditionEvidence": true,
  "source": "injected",
  "note": "《左传》通行本作「齐师伐我」，形近且义理不通（齐师代我）"
}
```

字段说明：

| 字段 | 必填 | 含义 |
|---|---|---|
| `start` / `end` | 是 | 错误点在原文中的**字符区间**（左闭右开）。判定以区间为准，不以字符串相等为准 |
| `original` | 是 | 该区间的原文，用于人读与自检（应等于 `text[start:end]`） |
| `expectedSuggestion` | 是 | 权威整理本的写法。异文类填**别本写法**，与 API.md §2 的契约一致 |
| `type` | 是 | 五类之一；通假类按"用字现象"标注 |
| `path` | 否 | 依据路径（形近/音近/义理/对文/版本），可多值。用于分析"模型靠什么发现" |
| `hasEditionEvidence` | 是 | 该点是否能凭版本判定。**异文类此字段为 false 时，模型报它也按存疑处理**（见 §3.4） |
| `source` | 是 | `ocr` \| `injected` \| `inherent`（通假/异文取自原文时用 inherent） |
| `note` | 否 | 依据与备注，进论文附录 |

## 3. 判定规则

### 3.1 匹配方式：以位置区间为主

模型返回的每条建议有 `offset` 与 `original`（API.md §2 保证 `original` 是原文子串、`offset` 由后端重算）。
判定"这条是否命中了某个 ground truth 点"，按**区间重叠**：

- 命中条件：模型建议的区间与 GT 点的区间**有重叠**，且**不是只重叠一两个字**——
  具体口径取「重叠长度 ≥ min(len(建议), len(GT)) 的 50%」，避免跨字误配。
- 一个 GT 点**只允许被命中一次**：多条建议命中同一 GT 点时，取区间重叠最大的那条为命中，
  其余算重复（不计入 TP，单列"重复条数"）。
- 一个模型建议**最多命中一个 GT 点**：命中多个时取重叠最大的。

**为什么不用"字符串相等"**：模型常给出带上下文的片段（`日学而时习之` vs `日`），
按字符串比会把它判成未命中，而它其实是对的。

### 3.2 检出与分类分开算

命中后，再看类型是否一致：

- **检出（TP）**：区间命中即算，不看类型。
- **类型正确**：命中且 `type` 与 GT 一致，单独统计为"类型准确率"。
- 这样分开之后，"检出率高但类型常错"和"检出率低但判得很准"是能被区分开的两种状况。

### 3.3 四项指标

| 指标 | 定义 | PRD 目标 |
|---|---|---|
| 准确率 precision | TP / (TP + FP) | — |
| 召回 recall（PRD 写作 F1 检出率） | TP / (TP + FN) | ≥0.8 |
| F1 | 2PR/(P+R) | — |
| 校正准确率 | 命中且 `expectedSuggestion` 也被采纳的比例 | ≥85% |
| 类型准确率 | 命中中类型判对的比例 | 观察值，不设目标 |

FP 的口径见 §3.4，**额外正确不计 FP**。

### 3.4 额外报出的合法校勘点（关键口径）

模型会报出 ground truth 之外的、**确有依据**的校勘点。实测例：`reg-006` 除注入的脱文外，
模型另报了「「冥」通「溟」（大海之义）」——《庄子》"北冥"的经典训释，属真学问。

处理方式：

1. 由**标注人复核**该点：有依据 → 记为 `extra-valid`，**不计入 FP**；
   无依据（如无别本支持的异文）→ 记为 `extra-invalid`，**计入 FP**。
2. `extra-valid` 的点在下一版数据集中**补进 ground truth**（记为 `inherent`）。
3. 报告指标时同时给出「含 extra-valid 的 P」与「不含的 P」两个数字，并说明差异来源。

**这条口径直接决定 precision 是否可信**，也是本规范里最需要评委理解的一点：
把真学问算成误报，等于惩罚模型"比标注人更懂"。

### 3.5 异文与存疑

- 异文类建议若**不能给出别本写法**（`suggested` 与 `original` 相同），后端 schema 闸门已直接丢弃
  （API.md §2），不会进指标——这本身就是"输出可靠性控制"的一部分，报告时说明丢弃条数。
- 若 GT 点 `hasEditionEvidence = false`，模型报该点按**存疑**记：不计 TP 也不计 FP，
  单列"存疑条数"。
- 异文类的类型判定若与 GT 不一致（例如模型判成通假），按 §3.2 只影响类型准确率，不影响检出。

### 3.6 不计入评测的差异（与 Prompt 口径一致）

以下**不算错误**，模型报出它们要计 FP，GT 也不标注：

- 异体字、避讳字、繁简转换造成的字形差异（Prompt 里已明确排除）
- 纯句读（标点）差异
- 同一人物/地名的不同称法（不涉及字形校勘）

## 4. 置信度分层报告

模型的 `confidence` 经规则修正（TECH_DESIGN §5：命中形近/通假字表 +0.1；<0.7 折叠为低置信）。
指标必须**分两层报**：

| 层 | 口径 | 用途 |
|---|---|---|
| 全部返回 | 所有通过契约校验的条目 | 反映模型原始能力 |
| 高置信（≥0.7） | 仅高置信条目，即"参与一键采纳"的那批 | 反映**用户实际会看到并采纳**的效果 |

如果只报全部返回的那一层，会掩盖"低置信里混着大量噪音"这一事实；评审关心的是用户实际体验。

## 5. 对比实验设计

（目标值见 PRD §6；此处定可比较性要求）

- **对比对象 ≥4 个**：通用大模型 ≥2（不同厂商）、领域微调模型（阶段三）、
  以及**消融**：去掉规则置信度修正、去掉 RAG（阶段二起）。
- **可比性要求**：同一批 GT、同一 Prompt 版本（记录 `collate_v2` 等版本号）、同一温度、
  `produceTranslation=false`（译文与校勘判定无关，关掉可减少变量与费用）。
- **每个对象跑全量数据集**，记录 CSV 列：
  `model,promptVersion,caseId,pointId,hit,typeCorrect,suggestionCorrect,extraValid,extraInvalid,confidence,dropped`

## 6. 效率实验

- 同一段文本 A/B：纯人工校勘计时 vs 本系统辅助计时，**各 ≥3 人**（PRD §6 要求提升 ≥3 倍）。
- 计时口径：人工组从拿到纸质文本到交出校勘记；辅助组从粘贴到导出校勘记（含采纳决策时间）。
- 记 `participant,group,elapsedSec,correctionsFound`，算提升倍数并给**置信区间**（人数少，别只报均值）。

## 7. 试点满意度

- ≥20 名文科学生，用后即填（模板见 `docs/SURVEY.md`）。
- **正向口径**：满意度题取 5 点量表，4–5 分计正向；目标正向比例 ≥80%（PRD §6）。
- 必须同时报告**样本量与回收率**，以及开放题的原话摘录（进佐证材料）。

## 8. 复现与版本记录

每次跑评测必须记录：数据集版本、Prompt 版本、模型名与供应商、日期、执行人。
评测脚本与原始 CSV 放 `docs/eval/`，脚本需能从干净仓库重跑出同样数字。
Prompt 改版时先跑 `server/tests/run_regression.py` 看是否退化，再决定是否重跑全量评测。
